# 长者健康数据与体征核查

日期：2026-09-04。原始诊断对象：`community-v1.0.0 / community-generator-v1.3.0`；后续修复对象：`community-generator-v1.4.0`。
结论：原始缺口见下文。v1.4 已修复 H01–H05 的 Fixture 行为并通过专项/全居民扫描；H06 只在隔离单人测试中接通，生产个人健康查询仍未放行。

## 本轮修复与实测

- H01：各居民按 seed/居民序号生成不同数值；no-record API 返回空体征/标签/测评，不回填默认值。
- H02：按居民内记录序号轮换 8 个指标：收缩压、舒张压、心率、血糖、血氧、体温、体重、步数。后两项属于健康/活动数据，不都称为生命体征；取值只为测试输入，不是临床阈值。
- H03：导出、最新体征、历史分页直接复用同一 entityRecord，ID/类型/数值/单位/时间完全一致，健康证据不再带金额/币种。
- H04/H05：按清单锚定日期实际过滤 1–365 天及测试指标；跨页使用全局稳定 evidenceId。stale/insufficient 保留过期与不足语义。测试专用 signsType 1–8 枚举不代表生产枚举合同已确认。
- 存储口径：为保持既有分片数量/稳定 ID，无记录及缺失部分保留 available=false、value=null 的占位行；清单的 120 个证据行/人是存储槽位，不是每个人都有 120 条有效健康测量。API 排除无效占位。不可把总行数当有效测量总数。
- 实测：健康专项 3 项覆盖 1,000 名居民；社区、选择及健康合计 18/18。全量 10,000 居民×16 Tool=160,000 次、192 个协议状态全部通过；报告 `QA-EXTERNAL/virtual-senior-community/health-v14-full-sweep-20260904/tool-sweep-report.json`。
- H06：单人 QA 专用 scenarioResolver → 原 Harness Policy → 独立 HTTP Fixture MCP → 原产品 ConversationScreen。真实 GUI 中 SYN-00231 完成本人健康体征查询；SYN-00001 返回无记录；匿名居民先要求身份授权。未调用付费模型、ASR/TTS、生产服务或新口型算法。
- 发现并修复健康 Tool 字符串 ID 转权限 Tool 整数 ID 的参数类型不匹配；权限规则仍不放宽。单人报告展开的循环引用白屏经实际点击复现并修复，新增回归防止再现。
- 仍待独立验收：真实生产身份/同意/指标枚举合同、完整医疗业务语义、个性化长对话、语音/口型、Windows 设备。上述扫描 PASS 不是这些层面的验收。

## 当前已包含

- MCP 合同：健康研判上下文、最新标签与体征、指标证据、研判结果保存、长者档案摘要、健康测评结果，共 6 个相关 Tool；读取/写入属于个人数据权限域。
- 数据类型：血压、心率、血糖、步数证据；健康标签；功能、营养、跌倒风险、认知测评；历史研判。步数属于活动数据，不把它等同于全部生命体征。
- community-full 清单可确定性生成 10,000 居民、80,000 健康标签、1,200,000 指标证据、40,000 健康测评、30,000 研判记录。这是生成器清单容量，不代表当前 App 已物化全部数据或每项健康语义已通过。
- 所有数据标记 synthetic-test-only；不是生产长者档案。

## 本轮实际执行发现

以 Node 调用 createCommunityDataset({profile:'community-full',seed:104729})，分别抽取 no-record、routine、multi-attention 居民；调用 toolResponse，并与 entityRecord 的居民序号记录对照。

| 缺陷 | 实际证据 | 验收影响 |
| --- | --- | --- |
| H01 固定体征及无记录语义失效 | 672900000/no-record、672900002/multi-attention、672900005/routine 的 vitalSigns 均为 systolic_bp=126 mmHg | 不能验证不同画像及无记录情境 |
| H02 横纵指标覆盖失真 | 以上居民分别枚举 120 条导出证据，类型各只有 systolic_bp、blood_glucose、heart_rate 一种；全局 index 取模叠加万人整除导致同一人只有单一类型 | 记录量大不等于单居民多指标历史丰富 |
| H03 导出与接口事实不一致 | 同一 evidence-672900000-1 导出为 systolic_bp=60 mmHg，接口为 blood-pressure=126/78；健康证据还夹带 amount/currency | 同一证据不能支持可追溯业务断言 |
| H04 时间过滤未执行 | timeType=1 和 180 返回的 evidence 数组完全相同，只有 timeWindow 文案变化 | 近一天/半年并未按记录时间筛选 |
| H05 分页证据 ID 重复 | cursor=0 与 cursor=2、limit=2 均返回 evidence-672900000-1/-2 | 跨页引用不可唯一追溯 |
| H06 个人健康查询未接通 | scenario-skills.cjs 将健康档案/健康报告等划到 health-general-guidance-v1，allowedTools=[] | 不能把一般健康问答当成健康 MCP 全链路验证 |

生成器给各指标共用 `60 + index % 80` 数值规则，未建立按指标区分的单位/数值/异常注入规则。例如合成 blood_glucose 记录出现 62 mmol/L；此处只说明无指标专属生成约束，不提供医疗判读。

## 为什么此前接口扫描不能替代此验收

当前 validateSuccessContract 主要检查必填与局部结构，健康测试部分对照 ID；timeWindows 断言只要求 evidence 非空。它们未验证数值、类型分布、实际时间过滤和无记录语义，因此历史结构扫描 PASS 不覆盖 H01–H06。

## 后续开发与验收要求

1. 同一居民共享健康事实源，导出、最新值、历史证据、标签、测评、报告必须一致。
2. 指标字典以站点 MCP 合同为准，不能凭空承诺血氧/体温等未落实的字段；逐指标定义单位、数据类型、时间、来源、质量和可控异常样本。
3. 支持正常、单/多项关注、无记录、缺失、陈旧、冲突、数据不足，状态必须真的改变数据与预期，不只是标签。
4. 时间窗按固定数据时钟过滤；跨页证据 ID 唯一；种子重放可复现；修订数据生成版本，不覆盖旧基线。
5. 个人健康意图与通用症状咨询分开；个人查询必须经过身份和授权，未授权不得读。不能为让测试通过而放开所有健康 Tool。
6. 方案 1 的完整资料、模拟接口、右侧交互及居民报告共享 resident/run/session 绑定；逐层区分数据检查、MCP、Harness、UI 与媒体验收。

状态：H01–H06 均未修复；本报告不据此提升工程总进度，不撤销其它独立范围已取得的历史证据。
